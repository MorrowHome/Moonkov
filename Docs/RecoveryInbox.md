# 撤离待领取区

正常账户库存保留 `InventoryCatalog.MaxItems=2048`。成功撤离时，服务器按完整顶层物品树尝试恢复装备/口袋，冲突时放入仓库；容量不足的树保存在独立、耐久的待领取区，不删除、不拆散，也不合并改写ID。领取只向仓库移动完整树。正常可容纳的部分先入库，剩余继续保存。

每个账户至多保留两份经过原库存规则验证的批次：本次撤出的剩余物品树，以及本次首次回收奖励。每批仍遵循原单图2048实体上限。待领取区非空时，服务器拒绝新部署，因此不能通过连续撤离无限增长；账户仓库整理、出售和领取保持可用。领取请求携带账户版本、待领取版本和独立请求ID，可领取一棵树或全部当前可入库物品。不够空间时保持原所有权。

任务产物即使仍待领取，也在当次撤离结算记录全局唯一来源、MissionRecovered和首次账户事实。首次奖励同样安全入库或进入第二批，领取不会再次发奖，领取后的产物可以按现有规则研究/出售。

## 事务和迁移

- PostgreSQL schema v8 新增 `inventory_recovery`，独立保存版本和JSON批次；已有账户缺行代表空待领取区，不改写原库存或历史结算。初始化重复执行安全。
- 同一个原结算事务内提交：结算回执、任务产物来源去重、账户正常物品、首次事实/奖励、待领取区、部署关闭。原回执重试只返回当前账户，不再次生成待领取物。
- 新增认证接口 `POST /auth/inventory/recovery/claim`。仍从会话取得账户身份，不能传目标账户。领取在玩家锁和数据库事务内写两份所有权及请求回执，重试/进程重启幂等。沿用 `inventory_trades` 回执表，但哈希加 `recovery/` 操作域，冲突不能当作成功。
- 账户Profile增加可选 `RecoveryJson`。客户端、服务端与持久化服务需同版本；`/internal/health` 增加 `recovery-inbox-v1` 能力。
- 离线读取兼容旧Format1缺 `Recovery` 字段的存档，按空区读取；第一次新版本写入迁移为Format2，旧程序会拒绝打开而非忽略待领取区再覆盖丢物；新档不能交回旧客户端。未知版本不会初始化新档或覆盖原文件/备份。保留原profile-v1.json路径，避免产生两个账户分支。结算/领取/回执仍一起写入临时文件并原子替换原存档。不会读取或重置用户真实存档进行验证。
- 新部署门禁保证正常已在途部署有预留的两批空间；不会在结算端把普通容量问题继续当作网络故障无限重试。无效来源、损坏存档、冲突回执仍拒绝，不能借溢出区绕过数据校验。

## 账户界面

仓库装备页面顶部显示待领取实体数、物品列表、整树领取和“领取全部可入库物品”。列表虚拟化，包含背包时说明包含内容；提示先整理/售卖再领取、领完才可再次出战。未完成领取保留原物品与明确失败反馈。沿用现有英文source→中文本地化，不修改设置页面或共享翻译生成器。
